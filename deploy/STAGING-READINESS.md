## Confirmed blockers

Source and regression tests now close findings 1, 2, 3, 4, 5, 8, and 9: certificate identity is TLS-subject-only with strict cardinality and conservative DN parsing; site/path are pinned locally; policy verification requires a readable key pin; 304 responses validate the installed lease; same-revision/different-hash responses fail; the agent propagates synchronization failure; empty site membership compiles an empty policy; and the runbooks describe the persistent signing helper plus the real environment-driven CLI. ### Closed on 27 October 2026

1. ~~Confirm the exact certificate-subject attribute and callback cardinality delivered by the installed FreeRADIUS version after a successful EAP-TLS handshake.~~ **CLOSED.** FreeRADIUS 3.2.5 (Ubuntu 24.04 `noble`, arm64) installed and live on a Raspberry Pi CM4 site appliance (`topline-freeradius1`, 192.168.13.54). The `python3_policy` module/post-auth hook was deployed per the (now-corrected, see `deploy/radius/README.md`) config and ran a real end-to-end EAP-TLS handshake using `eapol_test` (built from upstream `w1.fi/hostap` source) against a client certificate issued through this repo's own `app/pki.py` (subject `CN=eap-test-device1, O=<subsidiary-uuid>, OU=<network-role-uuid>`).

   Observed delivered attribute, verbatim from the FreeRADIUS debug log:
   ```
   TLS-Client-Cert-Subject := "/CN=eap-test-device1/O=11111111-1111-1111-1111-111111111111/OU=22222222-2222-2222-2222-222222222222"
   ```
   Single `TLS-Client-Cert-Subject` pair, OpenSSL-oneline format (`/CN=.../O=.../OU=...`) — matches `authorize_policy.py`'s `parse_certificate_identity` exactly. The adapter correctly returned `RLM_MODULE_OK` with `Tunnel-Type`/`Tunnel-Medium-Type`/`Tunnel-Private-Group-Id` reply attrs for a known binding, and the full chain reached `Access-Accept` (confirmed via `eapol_test`'s `SUPP_BE: SUCCESS` state). Test-only CA/cert/policy.json and build tooling (`hostap`, `eapol_test`) were removed from the CM4 afterward; the real `python3_policy` module wiring was left in place since it is the production config, not test scaffolding.

   Also found and fixed a real bug during this: `deploy/radius/README.md`'s config snippet had `mod_post_auth`/`func_post_auth` swapped, which fails module instantiation on FreeRADIUS 3.2.x. Corrected in the README.

2. ~~`policy.json` on the CM4 is not yet a real, hub-signed file.~~ **CLOSED.** The hub (`app/main.py`) is now actually deployed (Docker, behind Traefik, on `topline-server`'s 250GB Array B volume) with a bootstrapped root+intermediate CA, and `site_agent.py` runs as a real systemd timer on the CM4, pulling and installing a genuinely hub-signed, Ed25519-verified `policy.json` on every poll — confirmed via a real site binding (`topline` subsidiary, `staff` role, VLAN 10/fallback 99) flowing end to end into the installed file.

3. ~~Confirm... with a real issued cert, not a synthetic subject string.~~ **CLOSED — full real end-to-end device authentication proven.** Issued a real client cert through the hub's own `app/cert_service.py` (tracked in the DB, tied to the real `topline`/`staff` binding, proper department/role eligibility checks), ran `eapol_test` against the live FreeRADIUS, and got a genuine clean result: `MPPE keys OK: 1 mismatch: 0` / `SUCCESS`, no PMK mismatch warning. Two more real bugs found and fixed along the way:
   - The README's post-auth snippet had an `update outer.reply { &Tunnel-Type := &reply:Tunnel-Type ... }` block that is only valid in a tunneled EAP context (PEAP/TTLS inner-tunnel) — for plain EAP-TLS it's an undefined reference. FreeRADIUS logged `ERROR: Mapping "&reply:Tunnel-Type" -> "&Tunnel-Type" invalid in this context` and silently fell through to Access-Reject even though the module itself returned `ok` with the correct VLAN. Removed; the module's own returned attribute tuple is sufficient. Corrected in `deploy/radius/README.md`.
   - `CERTMANAGER_SITE_ID` must be the hub's `Site.id` (a UUID), not its `radius_cn`/hostname — a hostname value passes config validation and completes the TLS handshake, then silently rejects every request with a site-ID mismatch. Corrected in `deploy/radius/README.md`.

5. ~~The hardware inventory and real Ruijie Reyee RAP72/mixed-switch integration remain unverified.~~ **CLOSED for AP, open for switch.** FreeRADIUS's own TLS cert was reissued from the real intermediate CA (closing blocker 6 below in the same step), since the RAP72 and Windows wouldn't trust the distro snakeoil cert. Added a real `client rap72 { ... }` entry to `clients.conf`, configured the RAP72's own 802.1X server group and SSID (WPA2-802.1X) through the Ruijie Reyee cloud console, issued a real device cert (`victor-laptop`, tied to a real Device-less assignment for `topline`/`staff`), imported it into Windows, and joined the SSID. FreeRADIUS debug log confirms a full real TLS 1.2 handshake, `Access-Accept`, and `Tunnel-Private-Group-Id = "10"` delivered to the AP — proven with `freeradius -X` output, not just the DB/API layer. Two real deployment bugs found and fixed along the way: the issue form's `pfx` bundle silently disappears on a request_id dedupe (Back-button resubmit) with no explanation — fixed with a UI banner plus a bfcache-aware `request_id` regeneration; and every htmx write action (suspend/unsuspend/revoke/reissue) nested the entire next page inside the clicked button because a plain 303 redirect was never translated into `HX-Redirect` — fixed with one middleware covering all of them.    Switch/VLAN-trunk integration remains open: the RAP72 is plugged directly into a consumer ISP router with no 802.1Q support, so VLAN 10 was temporarily reverted to VLAN 1 (effectively untagged/no segmentation) at both the hub's `SiteRoleBinding` and the AP's SSID config, by explicit decision, to restore internet access for ordinary devices until a managed/L3 switch is in place. Re-enable real VLAN segmentation once that hardware is wired in.

9. ~~CRL push to the site was never actually wired up — `.env` referenced a private key (`RADIUS_SSH_KEY=/data/crlpush_id_ed25519`) that was never generated.~~ **CLOSED.** Generated the keypair, created a dedicated `crlpush` system user on the CM4 with a forced-command `authorized_keys` entry (`deploy/crlpush_forced_command.sh`, `deploy/authorized_keys.crlpush.example`), authorized it to reload `freeradius.service` via a new polkit rule (same pattern as the site-agent's). Found and fixed three real bugs in the process, none previously exercised against a live host: (1) the service's `$HOME` isn't writable by its non-root container user, so `StrictHostKeyChecking=yes` had nowhere to create `known_hosts` — pinned it next to the private key on the persisted volume instead; (2) `crlpush`'s login shell was `nologin`, which doesn't honor SSH forced commands (OpenSSH execs the forced command through the user's configured shell) — corrupted the scp byte stream until changed to `/bin/bash`; (3) OpenSSH 9+ clients default `scp` to the SFTP protocol, silently mismatching the forced-command script's legacy `scp -t` receiver — fixed by pinning `-O` client-side, and separately the script itself was redirecting `scp -t`'s stdout (which carries the protocol's ACK bytes back over the SSH channel) to `/dev/null`, hanging the client forever. Verified with a real push through the actual `app/crl_push.py` code path: `PushResult(ok=True, detail='pushed and verified')`, hashes matched on both ends.

10. ~~Nothing scheduled CRL regen/push — the code path and manual trigger worked, but no cron/timer ever ran it, so the "CRL is stale" banner never cleared on its own.~~ **CLOSED.** Wired `certmanager-crl.timer` (daily, `RandomizedDelaySec=600`) on the hub host, running `docker exec certmanager python -m scripts.regenerate_crl_cron`. First real run surfaced two more live bugs neither prior push test had hit: (1) the container's `extra_hosts` never mapped `RADIUS_HOST=topline-freeradius1` to anything, and the Docker-internal resolver can't see the LAN's own DNS/mDNS, so every push failed `Could not resolve hostname` — fixed by pinning `topline-freeradius1: 192.168.13.54` in `docker-compose.yml`'s `extra_hosts`; (2) the persisted `known_hosts` (added for blocker 9) pinned the host key under the IP only, but `push_crl` connects by the hostname from `.env`, so SSH found no matching entry and refused — fixed by appending a `topline-freeradius1`-keyed line for the same host key. Verified: `docker exec certmanager python -m scripts.regenerate_crl_cron` now exits clean with zero retry warnings in `docker logs`.
