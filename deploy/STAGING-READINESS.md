# Staging readiness review

29 October 2026. Status: BLOCKED for a live corporate pilot (no switch/VLAN trunk yet, no real DNS/HTTPS) but the full software chain, including a real access point, is now proven end to end against real hardware: hub deployed, real CA, real signed policy sync, real cert issuance, real EAP-TLS Access-Accept through a real Ruijie Reyee RAP72, a real device actually joining the Wi-Fi network at an authenticate-only site, and a real, working CRL push pipeline. Earlier completion claims predating this session were historical reports, not verified production readiness — this update is based on commands actually run against live systems today.

## Confirmed blockers

### Locally remediated on 26 October 2026

Source and regression tests now close findings 1, 2, 3, 4, 5, 8, and 9: certificate identity is TLS-subject-only with strict cardinality and conservative DN parsing; site/path are pinned locally; policy verification requires a readable key pin; 304 responses validate the installed lease; same-revision/different-hash responses fail; the agent propagates synchronization failure; empty site membership compiles an empty policy; and the runbooks describe the persistent signing helper plus the real environment-driven CLI. These are local test results, not proof of FreeRADIUS, Ubuntu, RAP72, switching, or DHCP behavior.

Found and fixed three real bugs in the process, none previously exercised against a live host: (1) the service's `$HOME` isn't writable by its non-root container user, so `StrictHostKeyChecking=yes` had nowhere to create `known_hosts` — pinned it next to the private key on the persisted volume instead; (2) `crlpush`'s login shell was `nologin`, which doesn't honor SSH forced commands (OpenSSH execs the forced command through the user's configured shell) — corrupted the scp byte stream until changed to `/bin/bash`; (3) OpenSSH 9+ clients default `scp` to the SFTP protocol, silently mismatching the forced-command script's legacy `scp -t` receiver — fixed by pinning `-O` client-side, and separately the script itself was redirecting `scp -t`'s stdout (which carries the protocol's ACK bytes back over the SSH channel) to `/dev/null`, hanging the client forever. ### Closed on 29 October 2026

11. ~~Real devices could never actually connect through the RAP72 — "Dynamic key exchange did not succeed" / "the root certificate used for this network is invalid" across every client, chipset, band, and AP firmware tried.~~ **CLOSED — real root cause found and fixed, not a client/AP issue at all.** A full day of live troubleshooting (three different laptops, MediaTek MT7902 and Realtek RTL8822CE chipsets, RAP72 firmware upgraded to ReyeeOS 2.420.0.2128, "Maximum Compatibility" enabled, 5GHz disabled, Roaming Aggressiveness disabled) never fixed it, because the actual failure was two independent server-side bugs, both found via a real `freeradius -X` debug trace against a live auth attempt, not simulation:

    - **`app/main.py` loaded the wrong CA as the trust root.** `ca-chain.pem` on the hub's PKI volume actually held the *intermediate* cert (`Topline Issuing CA`) under a misleading name — the real self-signed root sat at `root.crt`, untouched. `pki.load_cert_pem` only reads the first cert in a file, so `deps.root_cert` silently resolved to the intermediate everywhere it's used (Windows `TrustedRootCA` pinning, `.mobileconfig` trust anchors), reproducing exactly the Windows error `EAP Root cause String: The authentication failed because the root certificate used for this network is invalid` on every device, every time. Fixed: `app/main.py` now prefers `root.crt` explicitly, falling back to `ca-chain.pem` only if it's missing. Also fixed `Install.cmd`/`install.sh`/the onboarding zip to actually `certutil -addstore` *both* the root and intermediate into the real Windows trust stores — the old code only shipped the intermediate and never imported either cert into a trust store at all, the XML's thumbprint alone installs nothing.

    - **The real, decisive bug:** once client-side TLS trust was fixed, EAP-TLS started completing cleanly (confirmed via Windows Event 12012, "Wireless 802.1x authentication succeeded") but the connection still failed every single time at the WPA2 4-way handshake ("Dynamic key exchange did not succeed within configured time"). A live `freeradius -X` trace captured during a real connection attempt showed the actual cause: `deploy/radius/authorize_policy.py`'s `post_auth` decided accept/reject with `decision.outcome == "accept" and decision.vlan_id is not None` — but `evaluate_authorization` deliberately returns `vlan_id=None` on a real accept when a site has VLAN segmentation disabled (authenticate-only, no managed switch — exactly this site's configuration). The combined condition could therefore never be true at this site, so **every single authentication was silently rejected** regardless of certificate validity. The debug log read, verbatim: `Access-Reject: ... reason=Authorized: normal network role is ON (VLAN segmentation disabled at this site -- authenticate-only)` — the log line said Reject while the reason text said Authorized. This bug had existed since the VLAN-segmentation-toggle feature shipped (28 October) and made every authenticate-only site (the exact deployment shape this hardware pilot needs until a switch arrives) completely non-functional, while masquerading as a client Wi-Fi driver/AP firmware problem for an entire debugging session. Fixed: accept is now decided purely by `decision.outcome == "accept"`; the `Tunnel-*` reply attributes are only included when `vlan_id is not None`. Added a true end-to-end regression test that calls `post_auth` itself (not just `evaluate_authorization`) so this exact gap can't silently reopen — the two prior `vlan_segmentation` tests only checked the decision object, never that `post_auth` actually returned `RLM_MODULE_OK` for it.

    Both fixes deployed to the hub and to the CM4's auto-pulled `authorize_policy.py` (via `site-agent.service`, confirmed `radius-adapter: installed and verified` in its log), FreeRADIUS reloaded, and a real device connected successfully afterward. AP firmware upgrade and "Maximum Compatibility" are being left enabled (harmless, possibly helpful for other clients) even though they weren't the actual fix.

12. ~~An admin policy mutation (VLAN binding change, site authorization/deauthorization, VLAN-segmentation toggle) could sit un-delivered for up to 24 hours.~~ **CLOSED.** `publish_site_policy` only ever auto-fires inside `app/routes/site.py`'s `get_network_policy` (the site-agent's poll endpoint), and only when the current revision is missing or its lease has already expired — never on an admin data mutation itself. Found live while re-testing the VLAN binding change from item 11: changing a binding produced no new `SitePolicyRevision` row at all, meaning the fix for item 11 could in principle have been masked by a stale lease during testing. Added `republish_sites_for_subsidiary()` (`app/routes/web_helpers.py`) and wired it into `site_authorize`/`site_deauthorize`/`site_binding_configure` (`app/routes/web_subsidiaries.py`) and `site_set_vlan_segmentation` (`app/routes/web_sites.py`), so every mutation that can change compiled policy content signs and commits a fresh revision immediately instead of waiting on the lease. Added a regression test (`test_vlan_segmentation_toggle_republishes_site_policy`) that asserts the revision number actually bumps on each toggle. Deployed to the hub; `curl -sk https://localhost:8443/login` returns 200 post-deploy.

8. Root CA private key: backed up (encrypted, handed off), but the live data volume is on Array B, which SERVER_STATE.md documents as RAID0 — zero hardware redundancy. The encrypted backup was the only protection against a drive failure until today.

   **Confirmed live (30 Oct 2026) via `ssacli ctrl all show config detail` on the HPE Smart Array P408i-a:** Array A is 6×300GB SAS in RAID5 (1.36TB usable, 100% used by the OS alone), Array B is 2×1.2TB SAS in RAID0 (2.18TB usable, holds `/srv/data`). All 8 of the controller's drive bays are populated — **no spare bay exists to add a 3rd disk and convert Array B to RAID5**, and Array A has no free space to receive Array B's data even temporarily. Actually fixing this needs either a physical drive added to an as-yet-unconfirmed open bay elsewhere in the chassis, or a planned-downtime rebuild that repurposes a disk from Array A's badly-oversized 6-disk RAID5 — neither is something to do on a live production hub without a maintenance window.

   **Mitigated instead:** `deploy/backup_push.sh` (hub) / `deploy/backup_forced_command.sh` (CM4 receiver) now push a full nightly backup (DB + entire PKI including root/intermediate private keys, all issued service certs) from the hub to the CM4 over a dedicated, locked-down `certmanager-backup` SSH key (forced-command only, no shell — same pattern as the existing `crlpush` key), installed as `certmanager-backup.timer` (daily, `RandomizedDelaySec=600`). 30-day retention, pruned on the receiving end. Tested end-to-end (hit the same `scp` SFTP-vs-legacy-protocol mismatch as the original CRL push bug — fixed with `-O`): confirmed a 437KB tarball landed on the CM4. This doesn't fix the RAID0 exposure itself, but Array B dying no longer means losing the only copy of the data.
9. `WIFI_SSID` in the hub's `.env` is currently `radius-ap`, a test-rig value matching today's AP name — not final. When the real AP is renamed/configured for production, update that line and `docker compose up -d` (no rebuild needed) to match, or every generated Windows/Linux onboarding profile will target the wrong SSID (discovered live on 28 October 2026: a device couldn't connect because the installed Wi-Fi profile's SSID didn't match the AP's actual broadcast name).
